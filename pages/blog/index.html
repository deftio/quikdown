Building a Markdown Parser That Does More Than Parse

A compact markdown parser and editor built for humans and LLMs to work on the same document.

by deftio · quikdown v1.2.21

How quikdown started

I had a previous project, squibview, that was a split-view markdown editor built on top of marked. It worked, but it was heavy, and I couldn't control the fences the way I wanted. When I started building quikchat — a simple, flexible chat library — I found that integrating per-turn markdown rendering and a shared canvas for document editing was too difficult with existing parsers. The markdown layer was always either too big, too opinionated about rendering, or too hard to wire into a chat-style UI.

Around the same time, through 2024 and 2025, I was using a lot of different LLMs across different frameworks — Python, JavaScript, others — and the models kept putting out markdown with Mermaid diagrams, code blocks, and sometimes math or SVG. I just wanted to be able to interact with a model and have us both edit the same document.

It was important to have the document rendered so I could actually see things like diagrams, syntax-highlighted code, math equations, and inline SVG — not just raw fence blocks. quikdown was built to be compact and allow bidirectional editing. It lets the LLM see the document (using the quikdown API and tools) and operate on markdown, while the user can also operate on the markdown or the rendered content.

Of course markdown is much more valuable if it can be copy-pasted, so quikdown's editor allows copying and pasting rich content — including rendered fences — into Google Docs, Slack, Notion, and other rich-text apps. As an editor, quikdown is headless, so it can be embedded in web apps. Component builds are provided for ESM, UMD, and framework integrations including React.

quikdown also works offline. The standalone builds bundle everything into a single file for air-gapped use of most features without any network access. The core parser and bidirectional modules have zero dependencies of any kind, but the individual fences (e.g. Mermaid, MathJax, Leaflet maps) do use outside libraries. See the docs on how to manage those.

What fences actually solve

The core parser handles the usual markdown — headings, lists, tables, bold, italic, code, links — in ~17.1 KB with zero deps. Built-in fence support is what makes it more than just a bidirectional markdown parser.

A fenced code block in markdown is just triple backticks with a language tag. Most parsers hand you back <pre><code> and call it done. quikdown has a callback hook — your function gets the raw content and the language tag, you return HTML. The built-in editor ships renderers for:

  • Code with syntax highlighting (highlight.js)
  • Mermaid flowcharts, sequence diagrams, Gantt charts, git graphs
  • MathJax equations (LaTeX/TeX)
  • SVG rendered inline
  • CSV, TSV, PSV converted to HTML tables
  • GeoJSON on a Leaflet map
  • STL 3D models in Three.js
  • ABC notation as sheet music (ABCJS)
  • Vega and Vega-Lite data visualizations

The editor lazy-loads these libraries from CDN on first use — the initial bundle is ~102.9 KB. When someone hands you an 80-page doc with Mermaid diagrams, syntax-highlighted code, and a few LaTeX equations, the editor handles all of it without you writing integration code.

Writing a custom fence handler is a few lines:

const plugin = {
  render: (content, lang) => {
    if (lang === 'my-chart') return myChartLibrary.render(content);
    // return undefined for default code block rendering
  }
};

quikdown(markdown, { fence_plugin: plugin });

There's also a standalone build (~7.7 MB / ~1 MB gzipped) that bundles every fence library into a single file for offline or air-gapped environments. Same API, no CDN, no network.

Bidirectional: editing in the rendered view

quikdown_bd (~22.7 KB) tracks the original markdown syntax through the HTML using data-qd attributes. Edit the rendered preview — fix a heading, rewrite a table cell, change bold to italic — and call toMarkdown() to get markdown back. Fences, tables, and formatting survive the round-trip.

This is what makes the split-view editor more than a preview pane. Both sides are editable. The markdown stays the source of truth, but the human doesn't have to think in markdown if they don't want to.

// Convert with source tracking
const html = quikdown_bd(markdown, options);

// Edit the HTML, then convert back
const md = quikdown_bd.toMarkdown(html);

Undo/redo as a collaboration primitive

The editor maintains a configurable undo stack (default 100 states). Keyboard shortcuts work (Ctrl+Z, Ctrl+Shift+Z), and the API exposes undo(), redo(), canUndo(), canRedo().

This sounds like a table-stakes feature, but it matters specifically for the LLM workflow. When an agent writes into a shared document — via tool calling, MCP, or streaming — it will sometimes make mistakes. editor.undo() rolls back the last change without losing the rest of the editing context. It's also available as an MCP tool, so an agent can undo its own work.

const editor = new QuikdownEditor('#container', {
  undoStackSize: 200,   // max undo states (default 100)
  showUndoRedo: true    // show toolbar buttons
});

editor.undo();          // undo last change
editor.redo();          // redo
editor.canUndo();       // true / false
editor.clearHistory();  // wipe all history

Headless mode and the editor API

Set showToolbar: false and the editor becomes a pure API surface. Developers embedding quikdown can also choose to show only the markdown source, only the rendered output, or the split view — so the host application can look however it needs to. Split is just one of the view modes.

const editor = new QuikdownEditor('#container', {
  mode: 'split',
  showToolbar: false
});

editor.setMarkdown('# Hello');
editor.getMarkdown();          // '# Hello'
editor.undo();
editor.setTheme('dark');
editor.setMode('preview');

Wire the API to your own toolbar, your own keyboard shortcuts, or an agent's tool calls. The editor doesn't impose a UI — it provides the rendering, the undo stack, the fence plugins, and the bidirectional conversion. See the editor guide for the full API surface.

Streaming: re-parse the whole thing

quikdown's parser is fast enough that you can call it on the entire buffer for every incoming token chunk. No incremental parsing state. No "partial tree" to maintain. Incomplete fences render as plain text until the closing backticks arrive — no crashes, no garbled output.

let buffer = '';
for await (const chunk of llmStream) {
  buffer += chunk;
  editor.setMarkdown(buffer);
}

That's the whole integration. The editor handles fence rendering, scroll position, and undo grouping. See the streaming examples and LLM integration docs for production patterns with debouncing.

MCP server: 24 tools for AI agents

quikdown includes an MCP server that lets AI agents parse markdown, convert between formats, read/write files, and control the editor — all over JSON-RPC 2.0.

Headless tools markdown_to_html, html_to_markdown, markdown_stats, markdown_to_ast, markdown_to_json
Filesystem tools read_file_info, read_file_lines, write_markdown_to_file, write_html_to_file
Editor tools read_editor, write_editor, find_regex, replace_regex, undo, redo, get_rendered

The small things

Copy as rich text — copies the rendered preview to the clipboard with diagrams rasterized, tables intact, equations rendered. Paste into Gmail, Word, Slack, Notion. This is a small feature until you're doing it forty times a day.

Lazy linefeeds — single newlines become <br>. Models do this constantly. Toggle it on or off with lazy_linefeeds: true.

HR stripping — models love sprinkling --- between paragraphs. The editor has a tool that removes standalone horizontal rules without touching ones inside code fences.

Themes — setTheme('light'), setTheme('dark'), setTheme('auto') at runtime. Inline styles or CSS classes, your choice.

Structured output — parse markdown into AST, JSON, or YAML when your downstream isn't HTML.

Security model

All HTML is escaped by default. No eval, no dynamic RegExp, no innerHTML on untrusted content. URL sanitization blocks javascript:, vbscript:, and non-image data: URIs. The parser passes ESLint with eslint-plugin-security at error level with zero findings, enforced in CI on every build.

Trust is explicit: fence plugins receive pre-extracted content and decide what to render. The built-in html fence uses DOMPurify. Nothing reaches the DOM without an opt-in. See the full security model.

Architecture: four phases, no AST

The parser uses a four-phase pipeline: extract code blocks into placeholders, escape all HTML, line-scan for block elements + apply inline formatting, then restore protected content. No AST, no multi-pass regex — each line is classified once. This keeps the parser at ~17.1 KB and makes it straightforward to extend.

What it's not

Not a full CommonMark parser — definition lists and some edge-case syntax are intentionally omitted. Reference-style links and footnotes are available as opt-in features. Not a WYSIWYG block editor like ProseMirror or Notion. Not a framework with a plugin registry and a build system.

It's one npm install, one <div>, one import. The parser is a function. The editor is a constructor. The fences render diagrams, equations, maps, and 3D models out of the box.
